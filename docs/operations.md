# Deployment and operations

The local deployment is one Docker Compose stack, with persistent SQLite storage and optional monitoring. Default ports bind only to loopback. A [Railway shared demo](railway.md) uses a public HTTPS frontend with a demo code and a private API with persistent storage. Admitted demo visitors share one workspace; separate user accounts and tenant authorization are not implemented.

## Configuration

| Variable | Meaning |
|---|---|
| `MESH_API_KEY` | Required for live AI calls; keep local or in GitHub environment secrets |
| `MESH_MODEL` | Mesh model identifier; defaults to `openai/gpt-4o` |
| `DEEPDIVE_DATA_DIR` | Local data path; Docker uses `/data` on its research volume |
| `DEEPDIVE_API_TOKEN` | Shared local client/API credential generated by `ops init` |
| `DEEPDIVE_API_TOKEN_FILE` | Overrides the token with a mounted secret file in containers |
| `DEEPDIVE_API_URL` | Client destination; UI container uses `http://api:8000` |
| `DEEPDIVE_RELEASE` | Commit/release identifier attached to diagnostic/evaluation metadata |
| `DEEPDIVE_IMAGE` | Built local tag or published `ghcr.io/OWNER/REPO@sha256:DIGEST` |
| `SENTRY_DSN` | Optional sanitized exception reporting destination; empty means local only |

Run `uv run python -m deepdive.ops init` after checkout. It preserves existing credentials and refuses mismatched token files. Unix setup protects the secret directory and `.env`; Windows permissions inherit the local account's ACL. Individual Compose-mounted secret files must be readable by the non-root container UID. Protect the containing directory and never commit it.

Keep only one API worker. The service refuses a second owner of the same data directory. The UI is a client and does not open the database.

## Start, inspect, stop

```powershell
docker compose build api
docker compose up --no-build --wait --wait-timeout 180
docker compose ps
uv run python -m deepdive.ops health
uv run python -m deepdive.smoke
docker compose logs --tail 100 api
docker compose --profile monitoring down
```

The smoke command creates, renames, exports, and deletes its own session, checks memory writes and UI health, and makes no model requests. `down` preserves named data volumes. Avoid `down --volumes` unless intentionally discarding all stored research and monitoring data.

Readiness checks SQLite, a temporary write probe, and at least 100 MB of free disk. It does not contact Mesh or search providers. Liveness can be healthy while a provider is unavailable. A graceful stop requests cancellation and allows active calls to finish; the container stop grace period is 90 seconds. A forced stop may leave a run requiring explicit resume.

## Monitoring and errors

```powershell
docker compose --profile monitoring up -d
docker compose run --rm --no-deps --entrypoint promtool prometheus check config /etc/prometheus/prometheus.yml
uv run python -m deepdive.smoke
uv run python -m deepdive.monitoring_smoke --output evaluation/results/monitoring-smoke.json
```

Prometheus scrapes the API using its mounted token. Grafana has a provisioned Prometheus datasource and DeepDive dashboard for request rate, p95 latency, run states, queue age, dependency latency, verification outcomes, model calls, and tokens. Request labels use route templates, not question text or run IDs. Prometheus retains 15 days; Docker logs rotate at 10 MB with three files, and application JSON logs rotate at 5 MB with three backups.

The monitoring smoke command waits for startup and the first scrape/rule evaluation, then checks actual application metrics, all four rules, Grafana's database and datasource, dashboard provisioning, and every panel query through Grafana. It reads the generated admin credential locally without printing it. Empty research series are expected before any research runs; a missing API scrape or request metrics fails the check. GitHub CI starts the monitoring profile and retains this JSON result as `monitoring-evidence`. This checks the HTTP/data path; it does not claim a visual browser review or external alert delivery.

Four alert rules cover service unavailability, elevated API errors, stalled queue age, and repeated research failures. They appear in Prometheus. **External paging/email/Slack delivery is not configured.** Configure an Alertmanager receiver deliberately if operating a remote service.

Application logs contain timestamps, request/run IDs, entry point, event, and allowlisted operational fields. Local research audit records separately retain questions, cited text, and tool activity. `/errors` contains sanitized error IDs, types, fingerprints, and stack locations. Optional Sentry sends allowlisted diagnostic metadata without prompt text, request bodies, exception messages, or local variables; live Sentry delivery has not been validated here.

### Service unavailable

Check `docker compose ps` and API logs. Confirm the token file exists, `/data` is writable, disk has space, and no second process owns the data directory. After fixing the cause, restart with `docker compose up -d --wait`. Do not delete a database to clear an ownership error; stop its existing owner.

### Docker Desktop or WSL does not start

If Docker commands and every service endpoint hang together, inspect the host before changing application code. On Windows, `Get-PSDrive C` reports host free space. The container's readiness disk check sees its Linux filesystem, which does not guarantee free space on the Windows drive holding the growing VHD. Leave several GB of host space for startup and additional space for builds, stored research, and monitoring retention.

Stop Desktop before recovering a stale disk attachment. A `WSL_E_USER_VHD_ALREADY_ATTACHED` error can survive terminating only the `docker-desktop` distribution. Microsoft's [WSL disk documentation](https://learn.microsoft.com/windows/wsl/wsl2-mount-disk#detaching-a-disk) describes targeted detachment and `wsl --shutdown` when detachment fails. Shutdown affects all WSL distributions: inspect `wsl --list --verbose` and coordinate other workloads first. After host space and the attachment are resolved, relaunch Desktop and run both smoke commands above.

If bootstrap still reports that it cannot identify the filesystem, stop repeated restart attempts and preserve the data disk. Do not format, unregister, factory-reset, or remove volumes to clear the error. Follow Docker's [stopped-Desktop disk backup procedure](https://docs.docker.com/desktop/settings-and-maintenance/backup-and-restore/) before any repair that could change stored data. A disk error alone does not establish data loss.

### Request errors

Use the response `X-Request-ID` or `error_id` to find a local error record. Distinguish bad input (4xx) from unexpected service failures (5xx). Inspect recent code/configuration changes and disk/storage errors. Do not paste `.env`, full container environments, or private audit exports into public issues.

### Queue stalled

Inspect the active run and its timeline. Waiting for human review is a persisted state and should not occupy the worker. Check provider timeouts, cancelled work, and active-time usage. Cancel or explicitly resume the affected run after understanding its state; preserve the audit record.

### Research failures

Inspect retrieval outcomes and gateway errors. A missing/expired Mesh key, quota failure, search challenge, or blocked source can prevent completion. Add known public source URLs when discovery is blocked. Keep unsupported findings omitted; never weaken the verifier to make an alert disappear.

## Backup and restore

Backups contain private research, memory, source text, logs, and checkpoints. They are checksummed ZIP archives, **not encrypted archives**. Store them in an access-controlled, encrypted location. Credentials live outside the research directory and need a separate secure recovery method.

Stop the API and any evaluation command before backing up. For a local Python deployment:

```powershell
uv run python -m deepdive.ops backup backups/research.zip
uv run python -m deepdive.ops restore backups/research.zip restored-data
```

Restore requires an empty destination and validates every file hash and path before writing. Set `DEEPDIVE_DATA_DIR=restored-data` in `.env` before starting the recovered local service. Use a new backup filename for each snapshot. The command refuses a live service owner; it backs up SQLite through its backup API and checks database integrity.

For Docker, create `backups` first and stop the API. These commands use a one-off container with the same research volume:

```powershell
# PowerShell: New-Item -ItemType Directory -Force backups
# POSIX shell: mkdir -p backups
docker compose stop ui api
docker compose run --rm --no-deps -v ./backups:/backup api python -m deepdive.ops backup /backup/research.zip
docker compose up -d --wait
```

On a Linux host, grant the backup directory write access to UID 10001 before the command. To rehearse restoration safely, restore into a new host folder rather than overwriting the Docker volume:

```powershell
uv run python -m deepdive.ops restore backups/research.zip restored-data
```

Inspect the recovered history using a local backend configured for that path after stopping the Docker backend. The automated restoration test resumes a saved review and generates artifacts from the restored databases. A successful restore rehearsal is more useful than merely checking that a ZIP exists.

## CI/CD and release

Document ingestion and retrieval use the existing API process and research volume; there is no additional vector server. `MESH_EMBEDDING_MODEL` defaults to `openai/text-embedding-3-small`. `MESH_EMBEDDING_REVISION` defaults to `1`; increment it and start a new run after a deployment changes under the same model ID. Both values pass through Compose. Restart/recreate the API after changing them.

The first document run embeds missing chunks and records batch progress. All embedding/reranking attempts use the existing model-call budget, latency telemetry, and sanitized error handling. `document_retrieval` events retain candidate IDs and ranking-stage outcomes in the local audit. `document_rerank_fallback` exposes budget/schema fallback. Ordinary operational logs omit passage/query text.

The stopped-service backup includes document records, FTS tables, and vector BLOBs in `deepdive.sqlite3`. Parser subprocesses use temporary process memory; original uploads are not saved. Library removal retains historical citations and does not erase existing backups. See [document lifecycle and limits](rag.md).

The repository root must be the contents of `DeepDive`, so `.github/workflows` is at the GitHub repository root.

| Workflow | Trigger and gate |
|---|---|
| `quality.yml` | Main pushes/PRs/reuse: lint, contract types, compile, tests, fixtures, dependency audit, container startup and smoke, Prometheus config, monitoring HTTP/data path |
| `live-evaluation.yml` | Manual protected environment: Mesh verifier evaluation and independent-label quality gate |
| `release.yml` | Published release: quality workflow, fresh live evaluation, then build and push immutable commit-tagged GHCR image |
| `agent-arena-2026-checks.yml` | Organizer-supplied push checks; requires the organizer's submission token |

The public repository is [Ben-cod1ng/DeepDive](https://github.com/Ben-cod1ng/DeepDive). Main-branch protection requires `Quality checks` and `Docker smoke`, with up-to-date branches, linear history, and no force pushes/deletion. Administrator bypass remains enabled for the repository owner. Distinct check names avoid collision with the organizer's `checks` job.

The `live-validation` and `production` environments are configured with `Ben-cod1ng` as their required reviewer. Self-review is allowed for this single-owner repository. Set `MESH_API_KEY` in those environments and the organizer-required repository secrets before running live validation or release. No provider credential is supplied to PR quality jobs. On a fork/new repository, configure these protections explicitly; YAML environment names alone do not install reviewer policies.

Quality evidence is retained for 30 days; live/release manifests for 90. Release artifacts record the model/dataset/code hashes and published image digest. Dependabot proposes weekly Python, Docker, and Actions updates. Application Actions are pinned to commit SHAs; the organizer workflow is retained as supplied, with its own versioned action tags.

The pipeline prepares and publishes a deployment artifact. It does not pretend to have credentials for an unspecified host. On the chosen Docker host, initialize configuration, copy the release digest into `DEEPDIVE_IMAGE`, and record its commit in `DEEPDIVE_RELEASE`:

```powershell
docker compose pull api ui
docker compose up --no-build -d --wait --wait-timeout 180
uv run python -m deepdive.ops health
uv run python -m deepdive.smoke
```

## Upgrade and rollback

1. Record the current image digest and take a stopped-service backup.
2. Require passing CI and independent live evaluation for the candidate release.
3. Deploy its immutable digest and run health plus HTTP smoke checks.
4. Inspect error rates, queue age, and a reviewed research run before accepting the release.
5. On failure, restore the previous digest. If a release changed stored data incompatibly, restore its matching backup into a new directory/volume before starting the old image.

Do not silently change schema or assume an old binary can read future records. This initial release uses create-if-missing schema initialization; future schema changes need an explicit migration and restoration rehearsal. No availability SLO or recovery time has been measured yet. Plan for a brief maintenance stop during backup/deployment on this single-instance architecture.
